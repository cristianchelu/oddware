# LAN web UI

serves:
  - ../20-stories/scheduling.md
  - ../20-stories/connectivity.md
  - ../20-stories/feeding.md

## Purpose

When Wi-Fi STA has a routable IP, the device may serve a minimal HTTP control
panel on port 80 so the user can view today's schedule, edit the weekly
schedule, dispense manually, change feed mode, and set timezone — without a
MQTT broker or Home Assistant. `[design]`

No HTTP authentication or TLS in v0 — LAN access only, same threat model as
the open provisioning AP. `[design]`

## Compile-time gate

| Flag | Default (bring-up) | Meaning |
|------|-------------------|---------|
| `WEB_UI_ENABLE` | `y` in `feature.mk` | Admin UI on STA; set `n` before production release |

## Lifecycle

| Phase | HTTP server role |
|-------|------------------|
| AP provisioning (no stored Wi-Fi) | Captive portal only — see [provisioning-flow.md](provisioning-flow.md) |
| STA ready (`EVT_WIFI_STA_READY`) | Start admin UI on port 80 when `WEB_UI_ENABLE=y` and heap preflight passes |
| OTA download preflight | Stop admin HTTP (same window as [remote telnet](uart-console.md) suspend) |
| OTA failure resume | Restart admin HTTP when STA still ready |

Only one httpd role at a time: provisioning portal **or** admin UI, never both.

### Heap preflight

Before `http_server_port.start(80)` on STA, require
`xPortGetFreeHeapSize() >= WEB_UI_MIN_HEAP` (`[tune]` 24576 bytes). On failure
log `web ui skipped (low heap)` once per boot and do not start the admin UI.

## Static UI

| Method | Path | Response |
|--------|------|----------|
| GET | `/` | Pre-gzipped single-page HTML (`Content-Type: text/html; charset=utf-8`, `Content-Encoding: gzip`, `Cache-Control: no-cache`) |

Assets are built on the host (`tools/web/build.sh`) into
`firmware/src/web_ui_gz.c` (gitignored, regenerated by `build-firmware.sh` and
host tests). Client logic and tests: [web-ui-client.md](web-ui-client.md).
Target compressed size `[tune]` ≤ 12 KB.

## HTTP API

All `/api/*` routes return `Content-Type: application/json`. Mutation responses
use `{"ok":true}` or `{"ok":false,"error":"<reason>"}`.

Read payloads match retained MQTT state / command wire formats in
[mqtt-protocol.md](mqtt-protocol.md) unless noted.

### Reads

| Method | Path | Body |
|--------|------|------|
| GET | `/api/schedule/state` | Same JSON as `.../schedule/state` |
| GET | `/api/schedule/next` | Same JSON as `.../schedule/next` |
| GET | `/api/config` | Same JSON as `.../config` |
| GET | `/api/feed/mode` | Plain text `open_loop` or `compensated` (same as `.../feed/mode`) |
| GET | `/api/feed/overfill` | JSON `{"enabled":false,"threshold_g":50}` (same as `.../feed/overfill`) |
| GET | `/api/status` | Composite JSON — see [Status composite](#status-composite) |

#### Status composite

v0 exposes **one** status GET. The UI polls `/api/status` only (no per-topic mirror
routes). Field values use the same wire formats as retained MQTT topics in
[mqtt-protocol.md](mqtt-protocol.md). Telemetry strings are formatted from each
publisher module's last-known cache (`mqtt_*_sync` paths) — **not** live port or
sensor reads from the HTTP handler.

| Field | When present | Wire format (MQTT topic) |
|-------|----------------|--------------------------|
| `time_synced` | always | boolean |
| `local_time` | `time_synced` true | `YYYY-MM-DD HH:MM:SS` |
| `hopper` | always | `normal` / `low` / `empty` (`.../hopper`) |
| `dispense_busy` | always | boolean |
| `schedule_enabled` | always | boolean |
| `today_enabled` | always | boolean |
| `bowl_weight` | when publisher cache known | grams string or `""` unknown (`.../bowl_weight`) |
| `bowl_error` | when publisher cache known | boolean (`.../state`) |
| `battery` | when publisher cache known | `0`–`100` or `unknown` (`.../battery`) |
| `mains` | when publisher cache known | `ON` / `OFF` (`.../mains`) |
| `next` | when time synced and next slot exists | `{hour, min, g, in_min}` (`.../schedule/next`) |

Per-topic GET mirrors (`/api/bowl_weight`, `/api/hopper`, …) are **deferred**
past v0.

### Writes

POST body is the exact MQTT command payload for the equivalent topic.

| Method | Path | MQTT equivalent |
|--------|------|-----------------|
| POST | `/api/schedule/set` | `cmd/schedule/set` |
| POST | `/api/schedule/delete` | `cmd/schedule/delete` |
| POST | `/api/schedule/toggle` | `cmd/schedule/toggle` |
| POST | `/api/schedule/skip` | `cmd/schedule/skip` |
| POST | `/api/schedule/enable` | `cmd/schedule/enable` |
| POST | `/api/schedule/today` | `cmd/schedule/today` |
| POST | `/api/dispense` | `cmd/dispense` |
| POST | `/api/dispense/cancel` | `cmd/dispense/cancel` (no-op success when idle) |
| POST | `/api/feed/mode` | `cmd/feed/mode` plain body |
| POST | `/api/feed/overfill` | `cmd/feed/overfill` JSON body |
| POST | `/api/config` | `cmd/config` time slice (`tz_rule`, `tz_label`) |

Excluded from web API (MQTT-only): `cmd/ota`, `cmd/reboot`, `cmd/calibrate`,
`cmd/display`.

### Command routing

HTTP write handlers call the same `app_cmd_dispatch()` entry point as MQTT
(after topic classification). Schedule mutations go through `schedule_cmd.c`
shared with UART CLI and MQTT. UART CLI keeps human text output; HTTP and MQTT
use JSON.

## Security

No login in v0. Compile-time `WEB_UI_ENABLE=n` is the production mitigation.
The panel exposes the same control surface as MQTT schedule/dispense/config
commands on the LAN.
